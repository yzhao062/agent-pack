# Polish

This skill is the one entry for writing: an agent that drafts or revises prose a person will read runs it, so the rules and models that fit a draft reach it without the user naming another skill. A polish is a rewrite, and a draft is a rewrite from the sources. Its aim is prose that reads as the author at their best would write it. Writing well takes judgment and some invention. What the document says stays fixed, and how it says that stays open. When the choice is between a small safe edit and a rewrite, take the rewrite; step 4 checks it against the original and the sources.

This skill applies the whole writing harness, and every part reaches the draft through it:
- `AGENTS.md`: the Writing Defaults and Formatting Defaults, and the composed packs: `agent-style` with its House Style, the profile defaults, and `paper-workflow` with its Revision Discipline and venue conventions;
- the repository's `AGENTS.local.md` and every style source it names, such as a proposal house style or craft guide;
- the `author-voice` skill: section templates, exemplars from the author's own papers, and `voice_check.py`;
- the `/vet` review lenses in `implement-review/references/review-lenses.md`, and the banned-word list and detectors that `style-audit.py` runs.

Read them the way a writer absorbs a style guide and a shelf of good papers, then write from what they teach. The scripts check the result in step 4 and never set the plan. Resolve `implement-review` and `author-voice` through the skill lookup order in `AGENTS.md`. A path that begins with `scripts/` is in this skill's directory.

## Scope

- **Target.** The files the user names, and a section or one round's edits when named. Edit the named files in place, so `git diff` is the review surface for a tracked file. Run `git status` first and tell the user when the target already has uncommitted edits, since the diff will mix them with this pass. For a new file the user asks for, create it empty first. A draft asked for in chat, such as an email or a reply, is written in the session scratchpad and delivered in the reply, and the file steps (snapshot, comparison, `git status`) do not apply to it. Every intermediate file (a baseline, a content note, an alternative draft, a section copy, a probe script) goes in the session scratchpad, never in the repository.
- **One round's edits.** Stage the round to fix its baseline, and leave the pass unstaged so `git diff` shows it alone. The style audit without file arguments or `--all-lines` reads the staged copy, so it audits the round before the pass: it keeps line findings on changed lines and a document-level finding for each changed file. Step 4 audits the finished files by name. In a scratch copy outside git, audit each changed file whole and keep the document-level findings and the findings on changed lines. Never paste lines from several places into one file, since the detectors read it as one paragraph.
- **Kind.** A paper or proposal gets every step, including `voice_check.py`. Other prose a person will read (README, docs, report, email, reply) gets the same steps except `voice_check.py`. Typo, citation, and single-word fixes do not need this skill.
- **Mode.** *Draft* when the user asks for new text or the named section is empty or missing: the sources are the material the user names (notes, results, a solicitation, a thread) and the rest of the document. *Rewrite* is the default for existing text. `review` (or "just review") runs step 4's diagnostics on the existing text and stops after the step 2 plan. Run all steps also when `/polish` is one step of a larger task: a nested pass runs every step, and its report comes before the task goes on.
- **Writer.** When the user requests `/polish`, the coordinator that runs it edits the text, Claude Code or Codex, and that request overrides the profile pack's default that Claude drafts prose a person will read. For an automatic pass, the profile selects the writer, so a Codex or Agy coordinator hands the draft to Claude or the user. The content rules below bind every writer. A worker dispatched by `prun` or `/vet` does not run this skill.
- **Lead author.** `author-voice` reproduces the user's own voice. When a paper's lead author, or the author of a passage such as a co-PI's section, appears to be someone else, ask before applying `author-voice` to that text. Until the user agrees, that text and its local conventions are the voice model in steps 1 to 3, and step 4 skips `voice_check.py` for it; the rewrite, the style audit, and the content check go ahead.
- **Local rules.** Read the repository's `AGENTS.local.md` and any style source it names. Where they set a genre's conventions (a federal proposal's opening, a peer review's register, an email template's punctuation), they govern that draft.

## Content and Expression

- **Fixed: what the document says.** Every fact, number, citation, link, definition, and result stays in the document. A number keeps the quantity it states, with its unit, sign, and what it measures; rounding it, or stating a difference or ratio of two stated values, is expression, covered below. Each claim keeps its strength and scope and the qualifiers that bound it: a hedge or guarantee, a tie or loss, an unresolved gap with its reason, an exploratory or post-hoc status. A cause stays a cause, and parallel claims stay parallel. State only facts, results, citations, and relations that the document, or for a draft its sources, states. A change to what the document says goes to the author: a narrowed or reframed headline claim, an implication the body does not state, a move of prose to another section, or the correction of a stated fact.
- **Open: how it says it.** Word choice, sentence shape and length, voice and person, what a paragraph leads with, the order and grouping of sentences and paragraphs within a section, and the relation words that name relations the text states. Cut what carries nothing for the reader: repetition, an announcement of what comes next, a restated setup, a defense against an objection nobody raised, a caveat tail that adds no fact or reason, and a general limitation repeated outside Limitations (Risks and Alternatives in a proposal) when Limitations states it.
- **Open: how numbers appear.** The writer chooses which numbers the prose shows, at what precision, and how to explain them. A sentence may give a number at full precision, round it to the precision its claim needs, give a difference or ratio computed from two values the document states for the same comparison, or state the pattern and point to the table or figure that holds the values. It may say what a number means for the reader when that follows from its direction and unit (faster, cheaper, more accurate), and call a difference within noise when the document's own interval or test shows it. Keep in the prose the numbers that carry the claim. Any other number may leave the prose while a table, a figure, or another passage still gives its value; values that no display holds move into a compact table in the same section, or in its appendix when the page limit binds.
- **A summary section selects.** An abstract, introduction, or conclusion restates the body within the figure budget of the House Style and the `author-voice` template, and keeps its answer to the paper's main question with the population, the comparison, and every exception, tie, loss, or uncertainty that bounds it. It may leave out a detail when the reader gets the same answer at the same strength without it. An abstract or conclusion states the answer the body supports for completed work, or the question the work will test for proposed work, as its template says. It carries no pointer to a section, appendix, figure, or table, keeps the claim each pointer carried, and cites sparingly. Remove a citation only when the body credits the same work for the same claim and the section still shows whose result, comparison, or method it is. A pointer in a contribution head of the introduction moves into the sentences after the head.

## Steps

1. **Read before writing.** Record each target's word count, and for a revision the count in the last commit (`git show HEAD:<file>`). Read `AGENTS.local.md` and the style sources it names, the House Style and the `agent-style` rules in `AGENTS.md`, and the models that fit the text: for an abstract, introduction, or conclusion, the `author-voice` template and exemplars of that section and the body it summarizes; for another paper or proposal section, the House Style; for other prose, its sources and local conventions. For a draft, read every source. In `review` mode, also run step 4's diagnostics on the existing text now.
2. **Plan, in a message.** Read each paragraph whole, as its intended reader would, with what step 1 taught and the review lenses in mind (General items 7 and 8 for any prose; for a paper, the Paper preamble and items 1, 4, 7, and 8; for a proposal, the common proposal dimensions). *Redraft* is the default: give each paragraph or section in scope one line saying what the new version should lead with and what reads badly now, such as a late point, a transcribed table, stacked figures, a restated setup, more terms than a first read can hold, a broken thread, a voice that is not the author's, or an abstract or conclusion that lists steps where the body supports an answer. Mark a paragraph *keep* only when it already reads as the author at their best would write it. A page or line limit binds the whole section and is never a reason to keep a paragraph, since cuts elsewhere can pay for a line. List each unsupported claim, in either direction, and each fact to verify, with the evidence. For a draft, the plan is the outline instead: the question the text answers, the facts that carry the answer and their sources, and what leads; a chat draft keeps its outline in the scratchpad and goes straight to the text. Show a file's plan before any edit; in `review` mode add the diagnostics' summary lines and findings and stop here, and in a full pass go on without waiting.
3. **Rewrite.** For a file, save the targets first with `<python> scripts/content_check.py snapshot --repo <repo> --out <scratchpad>/<fresh-dir> <file>...`. Then, for each paragraph or section marked *redraft*, and for each part of a draft's outline:
   - Note in the scratchpad what it says, or for a draft what it must say: each claim with its strength and qualifiers, and each value, citation, link, definition, and stated relation, with its source for a draft, under the Fixed rules above.
   - Write it anew from that note and the section's purpose, in the author's voice, with the models from step 1. Do not carry over an old sentence shape out of habit. Decide what leads, what the prose shows, and how each number appears. Regroup or reorder paragraphs within the section when the thread needs it.
   - Where it matters most (an abstract, the opening of an introduction, a paragraph that carries a headline result, any paragraph whose first redraft still reads flat), write two or three versions that lead or build differently, and keep the one that reads best or combine their strengths.
   - Replace every banned word. In a rewrite, a claim the evidence does not support and a fact to verify stay as written and go to the author. In a draft, write what the sources support and report any open factual question.
   - Keep the format (LaTeX macros, labels, citations, comments, Markdown structure). A page or word limit binds the section's length: a paragraph that does not read well is still rewritten, and cuts elsewhere pay for its lines. When the text grows, say why in the report.
4. **Check against the original and the sources.**
   - Run the diagnostics on the finished text and, for a rewrite, on the snapshot for the before-and-after lines in the report. For a file, run `<python> <implement-review>/scripts/style-audit.py --repo <repo> --all-lines <file>`; for one round's edits, name the changed files the same way and keep only the document-level findings and those on lines that `git diff HEAD -U0` marks as changed. On a paper or proposal, also run author-voice step 4's `voice_check.py` on each section with its `--section` value, copying a section that shares a file into the scratchpad first. For a chat draft, run what applies to the text itself. Revise for a finding that points at a real problem, and keep a departure that reads well; never edit only to move a number in a script's report.
   - For a file, run `<python> scripts/content_check.py compare --repo <repo> --baseline <that dir> <file>...`. It lists each number, citation, link, label, cross-reference, and math expression whose count changed in a target, names nearby files that hold the same token, and marks a token absent from the target and the nearby files of the same type. Trace each change to where the document still gives that quantity: the same value in a table, figure, or passage; a rounding of it; the body passage a summary draws on; the target of a cut pointer; the body passage that credits a cut citation; or the table a value moved into. Trace a new difference or ratio to the two stated values it came from, and recompute it. For a marked token, look at the place the rewrite moved it to, and put the quantity back only when no form of it remains in the document. In a draft, every new token traces to its source.
   - Counts miss a swapped value, a lost qualifier, and a changed relation. Read the original section beside the finished one, cut and merged passages included, or a draft beside its sources: each claim at its strength and scope, each value still attached to its estimate, no inference added by joining two facts, and no count lost, even one written in words. After a correction, reread the corrected passage against its source or original, rerun any diagnostics the correction could change, and repeat the file comparison for a file target.
   - For a file, run `git status`: only the target files, and an appendix file that received a table in step 3, may show changes from this pass, and anything else the pass created moves to the session scratchpad.
5. **Deliver and report in the reply, never in the file,** when the pass ends. For a draft asked for in chat, the reply gives the text, then any open factual question and, briefly, the choices that shaped it. For a file, report the following.
   - Files and sections rewritten, and word count before and after, with the change against the baseline.
   - For each section, a few sentences on what the rewrite changed and why: what now leads, what was cut, how the numbers appear, which alternative was kept, and which rules or models shaped it.
   - The `content_check` summary line, each difference or ratio with its two values, each table added and where it sits, any quantity put back, and the diagnostics' summary lines before and after with any finding kept and why. The full trace stays in the scratchpad.
   - What goes to the author: each claim the evidence does not support and each fact to verify, with the evidence and the correction it supports, and each change to what the document says that the reading suggests.
   - Next steps: `git diff` to accept or discard hunks (for a new, untracked file, read it directly or run `git diff --no-index -- /dev/null <file>`), and `/vet` for an independent read before a submission.

Keep the run to one agent. An independent second read is `/vet`'s job, and this skill never dispatches it.
